# Embedding

What a CAD model can take from other Patchwork documents, and how that looks in the editor: [item 7 of the review](01-basic-idea-and-literature.md#problems-and-risks) ("decal, reference in a sketch, annotation"), widened to every way a document can enter a model. A report with suggestions, of which the first four steps of the [suggested order](#suggested-order) are built ([Implementation](#implementation)): imports of data, JS and files as text or bytes, the documents list and the document dialog for imports, titles in the code pane, following, pinning and locks; [linked values](17-parameters.md#values-from-other-documents) are listed too; documents dropped, pasted or inserted, with Import, Annotation and Canvas as roles, and values of them picked for number fields; annotations, pinned to faces, edges, features or the model and opened in Patchwork's embed frame; and canvases, images on origin planes or planar faces in the editor's view, with Calibrate. The reverse direction, a model embedded elsewhere, is done ([18](18-named-views.md#embeds)).

## Roles

A document can play several roles in a model; the role, not the document's type, decides where the reference is stored and how it is shown.

| Role | The document contributes | Typical documents | Stored in | State |
|---|---|---|---|---|
| Value | numbers and strings for parameters | JSON files, [datagrids](../.claude/skills/writing-patchwork-tools/reference/patchwork-experiments/datagrid/src/datatype.ts), any document's fields | code (import), or a configuration (`{ link }`) | done ([02](02-model-storage.md#imports-in-the-prototype), [17](17-parameters.md#values-from-other-documents)) |
| Code | functions, feature types | JS files | code (import) | JS done; feature types open ([02](02-model-storage.md#feature-types)) |
| Text, bytes | a file's content, for the roles below | any file | code (import) | done ([Files as modules](#files-as-modules)) |
| Sketch geometry | the curves of a drawing, as a profile | SVG, later DXF and tldraw drawings | code | [suggested](#sketch-from-a-drawing) |
| Text | a font's outlines | TTF files | code | later, with the above |
| Body | a solid or mesh | STEP and STL files, other models | code | with assemblies |
| Decal | an image on faces, part of the product | PNG, JPEG, SVG | code | [suggested](#decal) |
| Canvas | an image on a plane, to trace or compare | PNG, JPEG, SVG | the `cad` field | done ([Canvas](#canvas)) |
| Annotation | itself, shown at a place on the model | any document | the `cad` field | done ([Annotation](#annotation)) |

## Prior art

### In CAD systems

- **Fusion collects all of this in one Insert menu:** "Insert Component Insert Fastener Insert Derive Decal Canvas Insert SVG Insert DXF Insert McMaster-Carr Component Insert Mesh" ([Insert tools](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INSERT-TOOLS.htm)). Components and derives are linked: "It creates an associative reference to that design document. … When you edit the original design, the changes display in any assembly where it is referenced."
- **Decal and canvas are separate tools for the same image.** A decal belongs to the part: "Use Decal to apply a sticker-like image to a face. The Decal tool, unlike the Attached Canvas tool, can place an image on a curved face", optionally "Chain Faces to wrap the image across multiple faces", and "a Decal folder displays in the Browser with the image" ([Decal](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INS-DECAL.htm)). A canvas is an aid: "The Canvas tool places an image on a planar face or sketch plane. … If you want to reference the image as you design, select Display Through", and "Use Calibrate to scale your canvas to a specific size so you can use it as a reference for your design" ([Insert tools](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INSERT-TOOLS.htm), [Canvas](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INSERT-CANVAS.htm)).
- **Drawings become sketches, as copies in Fusion:** "The Insert SVG tool inserts an SVG file as a fixed sketch object in the current design. You can use SVG files to create detailed sketches like logos or text", and "A sketch is created and the image geometry is centered on the sketch origin" ([Insert SVG](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INS-SVG.htm)); for DXF, "One Sketch per Layer mode creates a separate sketch for each DXF layer".
- **Onshape links them:** "Insert DXF or DWG files into a sketch as sketch entities. The DXF or DWG must have already been imported into the currently open document (or another document you own or that has been shared with you, creating a link to that document)", and "the first dimension applied automatically scales the entire sketch" ([Insert DXF](https://cad.onshape.com/help/Content/Sketch/insert_dwg_or_dxf.htm)). An image in a sketch is a tracing aid ("Create sketch geometry using the image as a guide") that follows its source on request: "If the source of the image changes, it may be updated in its tab using the Update option on the tab context menu. This also updates the image wherever it is used in the document" ([Insert image](https://cad.onshape.com/help/Content/Sketch/insert_image.htm)).
- **Following or pinned is a choice, with a visible state.** Onshape: "When referencing a workspace, any updates to the master model update instantly. When referencing a version, updates to the master model must be versioned, and the reference must be updated to the new version. The version icon indicates when there is an out-of-date reference", and a version "allows you to decide when to rebuild the updates" ([Derived](https://cad.onshape.com/help/Content/PartStudio/derived.htm)); "Instead of changes to RefDoc propagating into UsingDoc with no recourse, you are informed when new versions are available and you choose whether to use them or not", and the source is a click away: "select Open linked document" ([Linking documents](https://cad.onshape.com/help/Content/linked-documents.htm)). Rhino's block definitions are "Embedded", "Embedded and linked" or "Linked", with "Always update", "Prompt when update required" and "Never update" for what happens when a model is opened, and "The icon appears behind the block definition name when the linked block is out of date. Click the icon to reload the block" ([Block](https://docs.mcneel.com/rhino/8/help/en-us/commands/block.htm)). Blender: "Link creates a reference to data in a source file such that changes made there will be reflected in the current file the next time it is reloaded", "Linked data-blocks are indicated with a chain icon in the Outliner", and "you can also Link/Append blend-files by dragging and dropping them into the Blender window" ([Link & Append](https://docs.blender.org/manual/en/latest/files/linked_libraries/link_append.html)).
- **Code-CAD imports by file name.** OpenSCAD's `import()` reads "2D geometry formats DXF PDF SVG" and "Data formats JSON", picks parts of a drawing ("For SVG import only, the id of an element or group to import"), and "PNG can be imported using surface()" ([Importing Geometry](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Importing_Geometry)). build123d's `import_svg(svg_file, *, flip_y=True, align=<Align.MIN>, ignore_visibility=False, label_by='id')` names what it reads: "XML attribute to use for imported shapes’ label property. Defaults to “id”", and `import_svg_as_buildline_code` is the copying variant: "Translate the contents of the given svg file into executable build123d/BuildLine code" ([Import/Export](https://build123d.readthedocs.io/en/latest/import_export.html)). KCL's modules include "Imports that read foreign files (STEP/OBJ/…)" ([Modules](https://zoo.dev/docs/kcl-lang/modules)). FreeCAD's spreadsheet gives values names: "Alias: Define an alias for this cell. This alias can be used in cell formulas and also in general expressions" ([Spreadsheet](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Spreadsheet_Workbench.md)).

### In document tools

- **Link or embed** is OLE's distinction: "Changes to data in the master file immediately affect the document that references it. This is called "linking" (instead of "embedding")" ([Wikipedia](https://en.wikipedia.org/wiki/Object_Linking_and_Embedding)). Transclusion is the linking half: "a resource is stored once and distributed for reuse in multiple documents. Updates or corrections to a resource are then reflected in any referencing documents" ([Wikipedia](https://en.wikipedia.org/wiki/Transclusion)).
- **Shallow or deep.** Embark: "Many transclusion mechanisms have a key limitation: they only support shallow view embeds. … the host is rendering a view without a deeper understanding of the data inside that view" ([Embark](https://www.inkandswitch.com/embark/)). In the [roles](#roles), an annotation is shallow, a view of the document; every other role is deep, the model uses the document's data.
- **One gesture, then the role.** Notion asks after a paste: "Copy and paste the URL. In the menu that appears, select Paste as bookmark", or "Paste as mention" ([Notion help](https://www.notion.com/help/embed-and-connect-other-apps)).
- **Updates are offered, not forced,** in Figma: "When library updates are available, the Libraries icon at the bottom of the navigation bar on the left will display a blue badge", and "Click Update next to an individual asset, or Update all to apply all updates" ([Figma help](https://help.figma.com/hc/en-us/articles/360039234193-Review-and-accept-library-updates)).

### Annotating 3D models

- **Sketchfab:** "Annotations are notes positioned in 3D space. They allow authors to provide information on a specific part of the model and tell a story" ([Viewer API](https://sketchfab.com/developers/viewer/functions)). Each has a camera: "you can mark different points on your model, record the best camera position, and add a description" ([announcement](https://sketchfab.com/blogs/community/want-your-models-to-tell-a-story-meet-our-new-annotations-feature/)); the API's `createAnnotationFromScenePosition( position, eye, target, title, text, [callback] )` takes "the position of the camera when the annotation is selected".
- **PMI** is the engineering form: it "conveys non-geometric attributes in 3D computer-aided design (CAD) and collaborative product development systems necessary for manufacturing product components and assemblies. PMI may include geometric dimensions and tolerances, 3D annotation (text) and dimensions, surface finish, and material specifications" ([Wikipedia](https://en.wikipedia.org/wiki/Product_and_manufacturing_information)). It is structured data on faces for machines and drawings; the annotations here are documents for people.
- **Comments** on faces, edges and features exist, with pins that follow the face and a list of detached threads ([13](13-collaboration.md#comments-1)).

### In Patchwork

- **A drag carries document URLs:** [`text/x-patchwork-dnd`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/sideboard/src/sideboard/dnd/payload.ts), the sideboard's `DndPayload` (`{ source, items: [{ url, name?, type?, toolId? }] }`, where "an item's `type` is the *datatype* id (e.g. "folder", "todo"), not a tool id", [openscad `dnd.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-experiments/openscad/src/dnd.ts)), `text/x-patchwork-urls` and `text/plain`, "so existing drop targets (sideboard, paper, space, markdown embed) accept them unchanged" ([universal-dnd](../.claude/skills/writing-patchwork-tools/reference/patchwork-experiments/universal-dnd/NOTES.md)). "Only `text/x-patchwork-urls` is guaranteed" ([tldraw5 `dnd.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/tldraw5/src/dnd.ts)). Our named views are dragged out this way ([18](18-named-views.md#in-the-editor)).
- **A host shows a document through the embed frame:** "chrome (title, tool picker, open button) around a nested `<patchwork-view>`. Hosts mount it via `<patchwork-view tool-id="embed">`, pin the inner tool with the `embed-tool-id` attribute" ([embed `tool.tsx`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/embed/src/tool.tsx)).
- **Each host stores the reference its own way:** markdown as text, "`[patchwork:docId]` or `[patchwork:docId/toolId]`", following by default: "No heads in the url: the embed follows whatever version the host resolves" ([`embed.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/codemirror-markdown/src/extensions/embed.ts)); tldraw as a shape with props, placed at the drop point, where a second drop of the same document selects the first: "Already embedded: select it rather than creating a duplicate" ([`tool.tsx`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/tldraw5/src/tool.tsx)); chat as `pendingEmbeds` of a message ([`InputArea.tsx`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/chat/src/components/InputArea.tsx)).
- **Comments can hold embeds:** a draft is "A cute.txt editor bound to the comment's `draftContent`. Replaces the plain textarea so drafts get the same rich plain-text (marks, emoji, embeds) that chat and notes use" ([`CommentThread.tsx`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/comments-view/src/CommentThread.tsx)).
- **The openscad tool is the deep one:** "Drag any Patchwork document onto the "Imports" bar above the editor to make its data available inside your `.scad` source as JSON", under "a sanitized, deduped identifier derived from the doc's title (click it to rename)", and "Imports are live: editing the source doc re-resolves and re-renders automatically" ([README](../.claude/skills/writing-patchwork-tools/reference/patchwork-experiments/openscad/README.md)). [02](02-model-storage.md#verdict-imports-in-code) keeps its gesture and puts the import in the code.
- **Files are documents** `{ name, extension, mimeType, content }` ([`types.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/file/src/types.ts)). Neither `mimeType` nor the type of `content` says what a file is: one dropped into the sidebar keeps its bytes whatever it is (`content = new Uint8Array(arrayBuffer)`) with the browser's type, `mimeType: file.type || "application/octet-stream"` ([`file-drop.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/sideboard/src/sideboard/document-list/file-drop.ts)), which an STL file gets; the file tool's own table knows SVG, PNG, JPEG, PDF, JSON and JS and has `mimeTypes[ext] || "text/plain"` for the rest ([`mime-types.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/file/src/mime-types.ts)).

## Principles

1. **What changes the result is code; what helps people work is tool data.** A sketch profile, a decal, a value are part of what the model is, so they are an import and a feature call, and the model stays a plain module ([02](02-model-storage.md#design-goal-portable-models)). A canvas and an annotation change nothing a build returns, so they sit in the `cad` field next to views and configurations, which "serve the tool" ([17](17-parameters.md#document-fields-and-portability)), anchored to faces as stored cameras and comments are (`RefData`, [`types.ts`](../src/cad/src/types.ts)). Fusion draws the same line between decal and canvas.
2. **Link, and show the link's state.** Every linking system above shows whether a reference follows its source, is pinned or is behind, and offers the update ("Visibility of System Status: The design should always keep users informed about what is going on", [NN/g](https://www.nngroup.com/articles/ten-usability-heuristics/)).
3. **Titles, not URLs.** "Minimize the user's memory load by making elements, actions, and options visible" ([NN/g](https://www.nngroup.com/articles/ten-usability-heuristics/)): `automerge:2owYJFe8…` says nothing, so wherever a document is referred to, its title and datatype icon are shown, and opening it is one click.
4. **One gesture, then a choice.** Dropping a document is the gesture Patchwork users know. Where it lands suggests a role only when the target is specific (a face, a field, a line of code); the user chooses, as in Notion's paste menu, and can change the choice later. A drag needs "feedback previewing what will happen before the user “drops” the object", and an alternative that isn't a drag ([NN/g](https://www.nngroup.com/articles/drag-drop/)).
5. **Nothing embedded can break the model silently.** A source that changes or disappears is an error at its import or a marked row, never a different part without notice.

## Suggestions

### Files as modules

Besides JS and JSON files and data documents, imports take any file as text or bytes, two kinds of module that cover every role in code ([`components/imports.ts`](../src/cad/src/components/imports.ts)):

```js
import logo from "automerge:2owYJFe8TQ9krQHCDVJgKfVXggLG" with { type: "text" };    // a string, e.g. an SVG
import label from "automerge:3RtmWqXcDkz8hPvN5sYbJ7uELfAa" with { type: "bytes" };  // a Uint8Array, e.g. a PNG
```

- **The attributes are the standard's, and runtimes are catching up:** Import Text is at "Stage: **3**" ([proposal](https://github.com/tc39/proposal-import-text)), Import Bytes at "Stage 2.7", "The bytes are returned as a `Uint8Array` backed by an immutable arraybuffer" ([proposal](https://github.com/tc39/proposal-import-bytes)). In Deno, text is "Stable as of Deno 2.8: no flag required", while "Binary `bytes` imports are still experimental" ([Deno](https://docs.deno.com/examples/importing_text/)). In Node, "Text modules are available behind the `--experimental-import-text` flag" ([ESM](https://nodejs.org/api/esm.html#text-modules)), "Added in: v26.5.0", "Stability: 1.0 - Early development" ([CLI](https://nodejs.org/api/cli.html#--experimental-import-text)), and for bytes "Support in Node.js is not yet implemented" ([Node 27 alpha](https://nodejs.org/en/blog/announcements/notable-v8-changes-from-node-js-26-to-27-alpha)). The devshell's Node 24.16.0 has neither (`bad option: --experimental-import-text`), so an [export](#export) can't rely on them yet.
- **The tool doesn't depend on browsers implementing them:** [`prepare.ts`](../src/cad/src/kernel/prepare.ts) replaces every specifier and its attribute with a blob-URL module, keeping the attribute's line breaks, so every line of the model stays where it was; acorn 8.19.0 parses the attribute. A `text` module is `export default "…"`; a `bytes` module's bytes go to the worker with the build, and its code reads them by the id of the document's version (`export default globalThis.patchworkCadBytes("automerge:…#heads")`), so that a file that didn't change stays one module, evaluated once ([`worker.ts`](../src/cad/src/kernel/worker.ts)). A document imported as several kinds, e.g. as text and as bytes, is a module of each.
- **The attribute is required.** Without it a non-JS, non-JSON file stays an import error, as a standard runtime would fail too, and the error names the attributes that would import it (`import it with { type: "text" } or with { type: "bytes" }`). `with { type: "json" }` is a browser's JSON module of a JSON file or any other document, with only the default export; any other attribute is an import error on its line that names the supported ones. The file's type is checked in the feature that uses it (`svg()` of something that isn't SVG is that feature's error).
- **A file is a document of Patchwork's `file` datatype** (`"@patchwork": { type: "file" }`, which the sidebar gives every upload, [`file-drop.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/sideboard/src/sideboard/document-list/file-drop.ts)), a CAD model, or a document without a datatype that has a file's `content` (text or bytes) and a `mimeType`, as JS libraries made by scripts are (`isFile` in [`components/imports.ts`](../src/cad/src/components/imports.ts)). Any other document is data, also one with a `content` key.
- **What a file is comes from its `mimeType` and, where that is generic or missing (`application/octet-stream`, `text/plain`, none), from its `extension`;** text is decoded from UTF-8 bytes, and bytes that aren't UTF-8 are a file that isn't text. So a JS or JSON file uploaded through the sidebar imports as code or data.
- **What files give:** SVG as text is a [profile](#sketch-from-a-drawing); an image as bytes is a [decal](#decal); a font as bytes makes text with replicad's `loadFont(fontPath: string | ArrayBuffer, …)` ("The font should be in TTF") and `drawText`; a STEP file is a body with `importSTEP(STLBlob: Blob): Promise<AnyShape>` and [`body()`](11-adopting-shapes.md#body) ([replicad.d.ts](../node_modules/.pnpm/replicad@1.1.0/node_modules/replicad/dist/replicad.d.ts)).
- **Model code stays synchronous.** The last two are `async` only for how they get their bytes: `importSTEP` awaits `STLBlob.arrayBuffer()` and `loadFont` a `fetch` of a path, while OCCT's `STEPControl_Reader` and `opentype.parse` are synchronous. With the bytes of an import in hand, the feature library reads a STEP file with the same OCCT calls, and a font given as an `ArrayBuffer` is registered before `loadFont` returns; both checked with replicad 1.1.0 in Node, a box written as STEP and read back, and `drawText` right after an unawaited `loadFont`.

### Sketch from a drawing

```js
const sketch2 = sketch({ plane: plate.end, body: plate, profile: svg(logo, { width: 40, center: [30, 20] }) });
const engraved = extrude({ sketch: sketch2, operation: "cut", target: plate, distance: 0.5 });
```

- **Linked, as Onshape, not copied, as Fusion:** the profile is computed from the document in every build, so a change of the logo rebuilds the model. `svg()` belongs to the feature library and parses in plain JS, so the model stays portable.
- **replicad draws what SVG paths describe:** its pen has lines, béziers and `ellipseTo(end, horizontalRadius, verticalRadius, rotation, longAxis, sweep)`, with "the long and sweep flags (as defined for SVG paths)" ([replicad.d.ts](../node_modules/.pnpm/replicad@1.1.0/node_modules/replicad/dist/replicad.d.ts)). It writes SVG (`toSVG`) but has no reader; JS prior art is [`@jscad/svg-deserializer`](https://github.com/jscad/OpenJSCAD.org/tree/master/packages/io/svg-deserializer) ("converts raw SVG formatted data (files) to JSCAD scripts or geometries").
- **It needs a richer `Profile`.** Today's is one closed loop, a polygon or a circle ([`feature.ts`](../src/features/src/feature.ts)); a drawing has several loops, holes and curves, and an extrude must be able to take one of a sketch's profiles or several. That is an item of its own, before constraints and the workflow of sketching ([00](00-status.md#not-started)), which build on it.
- **Segment ids come from the drawing,** as build123d's `label_by='id'` and OpenSCAD's `id`: an element's `id` names its loop, and its segments are numbered within it (`extrude2.side["leaf.3"]`). References then survive edits of the drawing that keep the ids, and break visibly otherwise ([03](03-topological-naming.md#recommendation)). An `only: ["leaf"]` option picks elements.
- **Size is explicit:** `width` or `height` in model units, or `scale`; Fusion's dialog has the same (position, angle, flip, scale), Onshape scales with the first dimension. The dialog shows the resulting size.
- **In the editor** it is a sketch like any other: the dialog's profile field shows the document's title, and the outline previews on the plane while dragging.
- **"Convert to sketch"** replaces `svg(…)` by its curves as code, once sketches can hold them: Fusion's behaviour, as the explicit way to cut the link.

### Decal

```js
const labelled = decal({ body: engraved, face: plate.side.front, image: label, width: 30, center: [0, 5], angle: 0 });
```

- **A feature, because a decal is part of the product:** it returns a new version of the body ([15](15-bodies.md#bodies-and-lineages)) that carries the decal, so later features keep it, parameters can place it, and an export can include it. The kernel never decodes the image: the body carries the placement and the image, and the viewer makes the texture.
- **Placement** is a face, a centre and angle in the face's frame, and a width; the height follows the image's aspect. They are set in the dialog. Fusion also has handles in the view ("use the manipulators to move, scale, rotate, and flip the image", [Insert tools](https://help.autodesk.com/cloudhelp/ENU/Fusion-Model/files/SLD-INSERT-TOOLS.htm)); those are a topic for all features together ([00](00-status.md#not-started)).
- **Rendering:** three's `DecalGeometry( mesh, position, orientation, size )` projects onto any mesh but "decal projections can be distorted when used around corners" ([three.js](https://threejs.org/docs/pages/DecalGeometry.html)). It is exact on planar faces, which is the first step; wrapping a cylinder needs the face's own parameterization.
- **It is the first appearance data on a body,** so it should be designed together with colours and materials.

### Canvas

- **An image on a plane or a planar face, drawn in the editor's view only:** `cad.canvases: { id, name, image: AutomergeUrl, plane: PlaneFrame | CadAnchor, center, angle, width, opacity, through }[]` ([`Canvas`](../src/cad/src/types.ts)). `through` is Fusion's "Display Through"; the height follows the image's aspect. The image's URL follows or is pinned as an annotation's ([Following and pinning](#following-and-pinning)).
- **The plane** is an origin plane's frame, moved along its normal, as `plane("XZ", 3)` makes it, or a face anchored as an annotation's is ([Annotation](#annotation)), which the worker locates in the shown bodies, so that the canvas follows the face through rebuilds. A face's frame is the one a sketch on it has, the world origin and X projected onto it (`frameOnFace` in [`features.ts`](../src/features/src/features.ts)), so that a canvas's coordinates are a sketch's there; the editor takes it from the face's mesh, without the kernel (`faceFrame` in [`model/canvases.ts`](../src/cad/src/model/canvases.ts)). A face that isn't planar, isn't shown here (e.g. past the timeline marker) or is gone from the whole model draws nothing, and the latter two mark the canvas's row.
- **Drawn as an image, never as markup** ([Security](#security)), once per version of its document, as a texture on a rectangle: translucent, in front of a face it lies on, behind the model or, through, over it. An SVG is drawn 4096 pixels on its longer side, its size from its `width` and `height`, else its `viewBox`, since Firefox draws one without width and height at no size.
- **Listed in the browser** under "Canvases", by name, with where it lies ("on XY", "on extrude1.end"), the state of its document, and an eye per user as bodies have ([15](15-bodies.md#visibility)), stored as `canvas:<id>` in the user's visibility; selecting one outlines it in the view and opens [the document dialog](#the-document-dialog) with its fields ([19](19-selection.md#the-selection)): Name; Plane, an origin plane with its Offset, or the face it is on, and Select face, which puts it on a planar face, centred there; Center, in the plane's coordinates; Angle about the plane's normal; Width, with the height it gives; Calibrate; Opacity; and Display through the model. They apply as they are typed, as a feature's fields do. Its context menu adds Hide or Show to the documents' actions.
- **Calibrate:** click two points of the image in the view and type their distance, as in Fusion; that sets `width`, about the centre. The points are crosses on the image, with a line between them, and the status bar says what to do next; a third click starts again, Escape or Cancel ends it, and a click in the view picks instead of closing the dialog.
- **Inserting one:** Canvas is a role for an image or an SVG in "Use as" ([The document dialog](#the-document-dialog)). It lies on the face the image was dropped on, centred where it was dropped, or else on XY under the model's centre; it is a round number about as wide as the model, and half see-through.
- **Not in the viewer tool and embeds:** a canvas helps the people modelling, and the viewer shows what the model is.
- **Other documents, live (experiment, branch `experiment/document-canvases`):** a canvas of a document that isn't an image shows it in a `<patchwork-view>` that three's `CSS3DRenderer` places on the plane, laid out 900 CSS pixels wide and scaled to the canvas ([`Viewer.tsx`](../src/cad/src/components/Viewer.tsx)); the 3D view's WebGL canvas lies above that layer and draws a transparent rectangle into the depth buffer where the document is, so that the model hides it where it is in front, which `CSS3DRenderer` alone can't ("It's not possible to use the material system of three.js", [three.js](https://threejs.org/docs/pages/CSS3DRenderer.html)). Found with [`experiment-document-canvases`](../src/harness/e2e/tests/experiment-document-canvases.spec.ts) in Chromium:
  - **Patchwork has no view-only mode, but a convention:** a handle at fixed heads is read-only (automerge-repo's `isReadOnly()`), and tldraw ("A history-pinned handle (url carries heads) is at fixed heads and rejects writes, so the whole tool renders read-only", [`tool.tsx`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/tldraw5/src/tool.tsx)) and CodeMirror ([`readOnly.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/codemirror-base/src/vendor/automerge-codemirror/readOnly.ts)) honour it. So a canvas shows the document at its current heads, and a new version mounts the tool again. Read-only isn't chromeless: tldraw keeps its page name and a smaller toolbar. The plugin contract has no preview, thumbnail or viewer flag (`ToolDescription`'s `tags` are `titlebar-tool`, `context-tool`, `frame-tool` and the like).
  - **What shows:** tldraw's shapes, with its camera as the tool last left it, not fitted to the canvas; a markdown document (`codemirror-markdown`) as its text; a data document in the `raw` tool's tree; a text or markdown file in the `file` tool as "No preview available for this file type".
  - **Chrome can be hidden by our stylesheet,** since tools render into the light DOM: `.tlui-layout` and `.tl-background` hidden leave tldraw's shapes alone on the plane. That is per tool and breaks with their class names.
  - **A `<patchwork-view>` first connected inside the `CSS3DRenderer` layer never mounts its tool** (its content stays empty, with or without `tool-id`), while one in the editor's own DOM does; connected again, it mounts. The cause is unknown; the experiment reconnects an empty one after 2 s.
  - **Not solved:** the document's own pointer events (the WebGL canvas lies above it), opacity (a document blends with the page behind it, not with the model, whose pixels its hole removed), and its height, which a document doesn't give as an image's aspect does.

### Annotation

- **Any document, pinned to a face, edge, feature or the model:** `cad.annotations: { id, doc: AutomergeUrl, tool?: string, anchor?: CadAnchor, view?: string }[]` ([`Annotation`](../src/cad/src/types.ts)). The anchor is the comments' ([`CadAnchor`](../src/cad/src/types.ts)), made the same way: a face or edge with its reference as data and as code and the feature that made it, a feature with its variable and statement, none for the model. A face's or edge's pin is where the worker resolves the reference against the shown bodies (`locate`, as for comments, [13](13-collaboration.md#comments-1)), so it follows the face through rebuilds and rollbacks; a feature's is on the faces it made in the shown bodies.
- **One pin per face or edge for everything pinned there** ([`components/pins.tsx`](../src/cad/src/components/pins.tsx)): its comment threads and its annotations, an annotation on a feature on the feature's first face. A pin shows an icon per kind, comments first, then each kind of document by its datatype's icon, and the total count if more than one of any kind is there; its tooltip lists them ("1 comment, notes, todo"). A hovered pin is outlined and highlights its face; it is filled while it is open, one of its threads is focused (e.g. in Patchwork's Comments panel) or one of its annotations is selected, and while its face is the selected one. The selected face or edge without a pin gets one with only the comment icon, which starts a thread there. A pin is a fixed 18px tall and ends 2px above the point it hangs from, so that it covers nothing there, e.g. the face a document is dropped on.
- **One pin for the model,** at the bottom left of the 3D view: annotations on the model as a whole, those whose place isn't shown (e.g. past the timeline marker), detached threads ([13](13-collaboration.md#comments-1)), threads on the whole document from Patchwork's panel ("Add comment"), and annotations whose feature is no longer in the timeline, or whose face or edge the whole model doesn't have; it is marked when any of them is gone. A feature of that name brings an annotation back.
- **Opening a pin** lists its threads, then its annotations, each an item with a border of its own, with its caption and buttons: a thread in Patchwork's `comment-thread` tool, whose Resolve and Reply are styled as the editor's buttons, an annotation in Patchwork's embed frame (`<patchwork-view tool-id="embed">`), with its title, tool picker and open button. The list scrolls, with a scrollbar of its own beside it ([`Scrolled.tsx`](../src/cad/src/components/Scrolled.tsx)), always shown, whose track takes the wheel, pages on a click and drags by its thumb, so that the list can be scrolled where an embed takes the wheel for itself: macOS overlays the browsers' scrollbars on the content and shows them only while scrolling, and neither Chrome (whose `::-webkit-scrollbar` styles give way to a standard `scrollbar-color`) nor Firefox can be made to show them otherwise; New comment is below it, also for a face or edge that only annotations are pinned to, which the worker names for the thread first. Each embed is made once per opening, so that a tool picked in it changes that embed alone; made anew on every change of an annotation, every embed went back to its default tool whenever one was picked. In the editor an open pin is the selection ([19](19-selection.md#the-selection)), shown as a dialog in the dialog area, titled as what it holds ("Comments and annotations on extrude1.end", "Annotations on the model"), which, as every dialog, lies over the pins and ends above the model's pin, which closes as any other; its face is highlighted, and so are the features that made it, in the timeline and the code, as if the face were hovered; an annotation hovered or focused in it marks its row in the documents list. Elsewhere, in the viewer tool, it is a popover at the pin, below or, where there is more room, above it, as high as the view has room; on the model's pin, a line above each says what it was on ("Face not found: extrude1.end", "Feature extrude1 deleted", "On extrude1.end, not shown here"). It goes to an annotation's view only if the pin holds just one annotation, which has one; otherwise each annotation with a view has "Go to view". The `<patchwork-view>` gets its height inline, as markdown embeds give theirs ("the stylesheet rule isn't reliably applied here", [`embed.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/codemirror-markdown/src/extensions/embed.ts)), since the frame fills its height; the tool picked in the frame (its `patchwork:embed-tool-changed` event, which goes no further) is kept in `tool`, and is an undo step, as a markdown embed's is an edit of its text. The viewer tool's popover follows its pin as the camera moves, to the annotation's view or by orbiting, kept within the view. In the editor each annotation has "Edit annotation", which selects its row. The viewer tool, models and embeds alike, shows them too ([`components/annotations.tsx`](../src/cad/src/components/annotations.tsx)).
- **Another CAD model** is an annotation shown with the viewer tool (`tool: "cad-model-viewer"`), as the editor has no place in a popover; the model itself can't be one, which the status bar says.
- **An optional named view** ([18](18-named-views.md)), as Sketchfab's camera per annotation: opening the annotation goes there. In an embed, that is a local orbit: Reset returns to the embed's view.
- **Not a comment thread,** although a comment can hold an embed: threads are discussions that get resolved, and resolved ones are hidden ([13](13-collaboration.md#comments-1)); a datasheet, a test report or a photo of the printed part should stay.

### Dropping, pasting, inserting

A Patchwork drag over the editor is recognised by its types, `text/x-patchwork-dnd`, `text/x-patchwork-urls`, `text/uri-list` and `text/plain`, and its documents are read from them in that order of preference, as the sidebar's [`payload.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/sideboard/src/sideboard/dnd/payload.ts) has them ("MIME types we can extract document drags from, in order of preference"), web links (`#doc=<id>`) included ([`dnd.ts`](../src/cad/src/components/dnd.ts)). A drop opens [the document dialog](#the-document-dialog), which offers every role the document allows; where it lands only preselects one:

| Dropped | preselects |
|---|---|
| on a face | Decal for an image, Sketch for an SVG, Annotation for anything else |
| on a plane | Canvas for an image, Sketch for an SVG |
| in the code pane, the timeline or the documents list | Import |
| on a number field | Import of one value; in a configuration, a link |
| elsewhere in the view | nothing |

Import, Annotation and Canvas are the roles so far ([`inserts.ts`](../src/cad/src/components/editor/inserts.ts), whose `ROLES` and `preselects` the other roles join, each with its own fields in the dialog). So a drop on a face pins anything but an image or an SVG there at once; an image or an SVG waits as a pending insert, which keeps the face and the point it was dropped at, where choosing Annotation pins it and Canvas lays it on the face; and the view shows no planes to drop on, so a drop elsewhere in the editor (the view, the rest of the browser, the toolbar) preselects nothing. While a document is dragged over a face, the face is highlighted as a hovered one, and the status bar says "Pin ‹title› to the face" or "Insert ‹title› to the face". A document pinned to that face already, by the face's name, is selected instead of pinned twice.

- **While dragging,** the target under the pointer is outlined as a pick target is: the code pane, the timeline, the documents list (shown while a document is dragged, also when the model refers to none), the number field, a face, or the view; and the status bar names what a drop there does ("Import ‹title›", "Insert ‹title›", "Use ‹title› for Distance of extrude1", "Link ‹title› to w"). Dropped data can't be read before the drop: in `dragover`, the HTML standard's drag data store is in "Protected mode", where "the formats and kinds in the drag data store list of items representing dragged data can be enumerated, but the data itself is unavailable" ([HTML](https://html.spec.whatwg.org/multipage/dnd.html#concept-dnd-p)); only in `dragstart` it is "Read/write mode". So the editor reads a drag's documents at its `dragstart` in the page, e.g. in the sidebar, and a drag from another window is "a document" until it is dropped.
- **A drop is accepted with an effect the drag allows,** or the browser cancels it: copy, unless the drag allows only move or link (the sidebar allows "all" and its list asks for "move", [18](18-named-views.md#in-the-editor)). Files from the desktop are Patchwork's, which makes file documents of them in the sidebar; the editor neither takes nor refuses them. A drag of only text, e.g. a link from another application, is taken where it isn't text and read at the drop; in the code pane and in fields it stays text.
- **A preselected role is applied at once,** and the dialog stays open to change it, as our dialogs "apply edits as they are made and have no OK or Cancel" ([19](19-selection.md#prior-art)). With nothing preselected, the document waits as a pending insert, a selection of its own ([19](19-selection.md#the-selection)), and nothing is written until a role is chosen; closing the dialog writes nothing. A role in code writes the import line, and later the feature after the marker ([07](07-poc-modelling-ui.md#the-timeline-marker)); the insert is one change and one undo step ([16](16-undo-redo.md)).
- **Import writes the statement after the model's last import,** wherever the drop was, so imports stay at the top. It imports in the first way `importKinds` allows, the one that makes sense as a value: code for a JS file, as a namespace (`import * as lib from "…"`), since a file may have no default export; data for a JSON file or any other document, and text for an SVG or another text file, as a default import; bytes for an image or another binary file. Code is pinned to the document's current version and everything else follows ([Following and pinning](#following-and-pinning)); both stay changeable in the dialog. The name comes from the document's title, without a file's extension, as openscad's "sanitized, deduped identifier": its words in camelCase without diacritics, after `_` if it would start with a digit or be a reserved word, numbered from 2 if any name in the model has it (`importName` in [`model/documents.ts`](../src/cad/src/model/documents.ts)). Several documents dropped where Import is preselected are all imported in one change, and the first is selected; elsewhere the first is offered, and the status bar says the others were left out.
- **A document already imported the same way** is not imported twice: its row is selected, as tldraw selects the existing shape. Dropped elsewhere in the editor or pasted, a document the model imports already waits as any other does, since it may be meant as an annotation; Import then selects its row. A CAD model, or anything else that can't be imported, is a message in the status bar when Import is preselected, and nothing is written.
- **Dropped on a number field** (a feature's argument, a parameter's default, a configuration's value), a whole document doesn't say which of its values is meant, so the pending insert's dialog is about a value for that field alone: it has no "Use as", whose Import would leave the field, and its preview is the picker. The numbers in its data tree are buttons, the branches that lead to them are open and marked, and nothing is written until one is clicked. They are searched depth first, through the 50 keys of each level the tree shows and at most 5000 values, and the first 20 found are opened (`fittingValues` in [`components/imports.ts`](../src/cad/src/components/imports.ts)). A JS file's tree is its exports, as far as they are JSON: the kernel worker runs its module, with the documents it imports, at the version the model imports it at, else its current one (the `exports` request in [`worker.ts`](../src/cad/src/kernel/worker.ts)); a file that throws is a problem line. Where none can be picked, a problem line says why, naming the document and the field (`pickProblem` in [`inserts.ts`](../src/cad/src/components/editor/inserts.ts)): "‹title› has no number to use for Distance of extrude1" only if the search covered all of it; that it is still loading or can't be loaded; that it is a CAD model, or an SVG, image, text or binary file, which has no number to use for the field; or that it is a file a configuration's value can't link into. A configuration's value then links to it, `{ link: "automerge:<id>/rows/@1/width" }`, as a pasted URL does ([17](17-parameters.md#values-from-other-documents)), in automerge-repo's path syntax (keys, `@index`), written by its own `stringifyAutomergeUrl`. A feature's argument or a parameter's default becomes the expression that reads it, with its import, in one change ([`valueReference`](../src/cad/src/model/documents.ts)): a top-level key as a named import (`import { height } from "automerge:<id>"`, with `as` where the name is taken or the key isn't an identifier), a deeper value as a default import of its URL with the path (`import width from "automerge:<id>/rows/@0/width"`), and, where the model imports the document whole already, a member expression of that name (`dims.rows[3]["hole depth"]`). A file's content isn't addressed by paths, so a deeper value of a JSON file is a member expression of the whole file's import. A JS file's value is an export, or a member of one: of its namespace import where the model has one (`lib.hole_diameter`), else of a named import of the export, pinned to the file's current version as Import pins code (`import { hole_diameter } from "automerge:<id>#<heads>"`). The field's feature or the parameters are selected again. A drag whose URL already names a number ([17](17-parameters.md#values-from-other-documents), "Picking a link") needs no pick and is written at once. Fields that aren't numbers take no drops.
- **The same pick without a field:** a pending insert dropped elsewhere picks any value of its tree, which imports only that, by the same rules, while Import imports the whole document. A document's own dialog, opened from the list, keeps its tree a preview.
- **A drop on another tool's view is that tool's,** e.g. on a comment's draft, which embeds the document: threads are Patchwork's `comment-thread` tool in our popover as in the Comments panel ([13](13-collaboration.md#comments-1)), and the editor leaves drops inside any nested `<patchwork-view>` alone, as tldraw does ("If the drop lands inside an already-embedded <patchwork-view>, let that inner tool handle it", [`tool.tsx`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/tldraw5/src/tool.tsx)). The popover closes on a click outside, not a press, so that a drag from the sidebar keeps it open. The editor's own drags of a named view ([18](18-named-views.md#in-the-editor)) insert nothing in it; drags of a document row ([The documents list](#the-documents-list)) drop in it as any document does.
- **Without a drag:** "Insert" in the toolbar opens the dialog with an empty document field, which takes a pasted `automerge:` URL or web link, or a drop; then it is a pending insert as one dropped in the view. Pasting such a URL while the view, the browser or the timeline has the focus opens the dialog with that document; in a field, the code pane, a dialog or another tool's view, a paste is text.

### The document dialog

One dialog for a document in a model. It opens when the document's row in [the list](#the-documents-list) is selected ([19](19-selection.md#the-selection)), for a pending insert on a drop, a paste and from "Insert" ([Dropping, pasting, inserting](#dropping-pasting-inserting)), and is to open from a feature's document field.

| Document | Use as | As |
|---|---|---|
| image file | Decal, Canvas, Annotation, Import | bytes |
| SVG file | Sketch, Decal, Canvas, Annotation, Import | text, bytes |
| JSON file | Import, Annotation | data, text, bytes |
| JS file | Import, Annotation | code, text, bytes |
| any other file | Import, Annotation | text (if its content is text), bytes |
| any other document | Import, Annotation | data |

- **Document:** its datatype icon and title, which opens it, and its URL, where a pasted `automerge:` URL or a drop replaces the document in the import, or gives a pending insert its document.
- **Use as:** the roles the document allows, wherever it was dropped, so a JS file or a datagrid dropped into the view can become an import; not for a pending insert dropped on a field, which is about a value for it. A pending insert has none chosen; choosing one writes it and selects what it made, the document's row for Import. It is to be changeable while no other feature uses what the role made; the feature or entry is then replaced.
- **As,** for a role in code: how the model gets the document ([Files as modules](#files-as-modules)), Data, Code, Text or Bytes as the table allows. A sketch needs text and a decal bytes; for an import it is a choice, also later, which rewrites the import's attribute and nothing else. A feature that then gets the wrong kind is an error at its call.
- **A preview of what the model gets** tells the kinds apart: data as a tree of keys and values, text as its first lines, bytes as their size and, for an image, the picture, code as its exported names. It renders only what is shown: a tree's levels when they are opened, 50 keys each, 8 lines of text, 160 characters of a value or line, and images up to 8 MB. In a pending insert, the tree's first level is open and a click on a value uses only that ([Dropping, pasting, inserting](#dropping-pasting-inserting)): a top-level key as a named import, a deeper one by its path in the URL ([17](17-parameters.md#building-blocks)).
- **Name:** the import's local name where the statement has a single default or namespace binding; renaming it renames its uses, as renaming a feature does. Named imports are listed. An inserted import gets a name derived from the document's title, as openscad's ([Dropping, pasting, inserting](#dropping-pasting-inserting)).
- **Version:** Following or Pinned, and Update when pinned and behind ([Following and pinning](#following-and-pinning)).
- **What uses it:** the features, the parameters, the configurations that link to it, or the imported file that imports it, each of which selects that.
- **Below, the role's own fields:** the feature's form for a sketch or a decal, a canvas's placement, an annotation's anchor, tool and view; none for an import. An annotation's "On" chooses the model or a feature of the timeline, and "Select face" or "Select edge" pick one in the view, as a feature's field picks; "Tool" names the one picked in the embed frame, with Reset; "View" chooses a named view, which the camera then goes to, or none. "Show" opens it next to its pin.
- **A document with several uses,** opened from the list, lists them in place of "Use as"; each selects its feature or entry.
- **A linked value's document and one an imported file imports** have only what applies: the document, its state and what uses it.

### The documents list

A "Documents" section in the [browser](15-bodies.md#the-browser), the place Fusion shows decals and canvases and Blender and Rhino their links: every document the model refers to, whether from an import, an import of an imported JS file, a linked value or an annotation; the images of canvases have a "Canvases" section of their own, with the same rows by the canvases' names ([Canvas](#canvas)). A row is an imported module, named by its URL without heads and the type it is imported with, so that pinning it keeps it the same row and selected ([`model/documents.ts`](../src/cad/src/model/documents.ts)); an annotation is a row of its own, named by its id, with where it is pinned after its title, as a document may be pinned to several places.

- **A row** shows the datatype icon, the document's title, as its datatype's `getTitle` gives it, with the path its URL names after it, and its state as an icon with a tooltip: following (chain), pinned (pin), newer version available (dot), unavailable (warning), held back by its lock (lock, with the errors the newer version brings). Documents of imported files and of linked values are indented, the former muted. Patchwork has no element that draws a datatype's icon by its lucide name, so the editor has the few it needs, and a file's icon says what it is ([`icons.tsx`](../src/cad/src/components/icons.tsx)).
- **Hovering or selecting a row** highlights the features that use it in the timeline, the browser and the code, and a hovered row also what they made in the view ([`usersOf`](../src/cad/src/model/documents.ts), with the dependency analysis of [`deps.ts`](../src/cad/src/model/deps.ts); [12](12-hover-highlighting.md)); a feature uses a document if it reads a name the import declares, or a derived value that does. Selecting a row opens [its dialog](#the-document-dialog).
- **Hovering or selecting a feature** highlights the rows of the documents it uses, and "Edit ‹document›" in its context menu and its dialog selects the document, as "Edit ‹feature›" on a face selects its feature ([19](19-selection.md#the-selection)).
- **A grip (`⠿`) drags a row's document,** as the named views' grip does ([18](18-named-views.md#in-the-editor)), so that a document the model uses can be reused without Patchwork's sidebar: with Patchwork's payload (`text/x-patchwork-dnd` with its URL, title and datatype, `text/x-patchwork-urls`, `text/plain`), allowing every drop effect. It carries the URL with the path its import names and without heads, a pinned one too: dropped elsewhere in Patchwork it is the document as it is now, as the row's title shows it, and dropped on this model it finds its import, whose id has no heads either ([`rowDragUrl`](../src/cad/src/components/editor/documents.ts)). On a number field, the pick then reads the import there is (`sizes.height`); on the code pane, the timeline or the list, its row is selected; in the view, it waits, and Import selects its row. A document an imported file imports is not the model's own import: dropped where Import is preselected, it is imported. A linked value's document carries no path, so that a drop on a field offers its values.
- **Its context menu** has the dialog's actions that need no field: Open, Show (an annotation), Follow or Pin to this version, Update (when pinned and behind), Remove (when nothing uses it; it deletes the import statement, or the annotation). Entries that don't apply are left out, as in the other menus.
- **In the code pane,** the title is shown after the specifier as a widget that opens the document; the stored text stays the URL. The import of a held-back document is marked as the line of an import error is.

### Following and pinning

The URL says which: without heads it follows, with `#heads` it is pinned ([02](02-model-storage.md#versioning)), in code and in the `cad` field alike. Pin, Follow and Update rewrite the URL, which for an import is a splice of the specifier.

- **A choice per document,** made in [its dialog](#the-document-dialog) when it is inserted and changeable there later. Both are needed for every kind: following code is "useful for prototyping and testing" ([02](02-model-storage.md#versioning)), e.g. a library written next to the model, and a pinned logo is a released part's.
- **The default is pinned for code and following for everything else.** For feature types, pinned is already the default ([02](02-model-storage.md#versioning)), and an import of JS runs it ([Security](#security)). A logo or a table of values edited next to the model is expected to arrive, as Patchwork's markdown embeds follow and as Onshape's FeatureScript imports within a workspace "will update automatically when the imported tab is changed" ([02](02-model-storage.md#versioning)).
- **Pin, Follow and Update** change every import statement of the module together, each one splice and one undo step; Pin writes the version the model is built with, Update the document's current one.
- **"Newer version available"** is a pinned URL's heads differing from the document's current ones, which the documents list loads anyway for the title ([`documentInfo.ts`](../src/cad/src/components/documentInfo.ts)).
- **A following document is locked to the version the model last built with:** `cad.locks: { [url: AutomergeUrl]: heads }`, keyed by the document's URL without a path or heads, so that one version of a document is built with however many imports name parts of it ([`model/locks.ts`](../src/cad/src/model/locks.ts), [`createModel.ts`](../src/cad/src/components/createModel.ts)). A following document is built with its latest version. If that build has an error the build with the locked versions doesn't have, the model is shown as built with the locked versions, and the document's row, its import in the code pane and the status bar carry the errors ([principle 5](#principles)); otherwise the lock advances. Documents that moved at once are held back together. Documents imported by an imported JS file are locked the same way; a pinned import needs no lock.
- **Two builds' errors are compared by what they are about, not their messages,** which name values and versions: an error of the build by its kind and line (`import error on line 2`), a broken or failed feature by its status and name (`failed fillet1`); a runtime error without a line counts as the kernel's, and meshing isn't compared, since the other build is a trial without meshing (`check` of the worker). The latest versions are built first; only if that build has errors is the locked one tried, and only if it is held back is the locked one built to be shown. While a document is held back, the locked build goes first.
- **The first lock** is written with the first build, whatever its errors: there is no locked build to compare them with, and later versions are compared with this one.
- **Locks only advance:** a lock is written only if it differs from the stored one and every head of the stored one is in this copy of the document's history. An editor that hasn't synced the version another editor locked is behind it: it builds with what it has and leaves the lock alone. Otherwise two editors with different versions of a document would overwrite each other's lock forever; editors in step write the same lock.
- **Only the editor writes locks,** and never into a model shown read-only, e.g. at an old version (automerge-repo's `isReadOnly()` of a handle with fixed heads). The viewer and embeds build with the latest versions and fall back to the locks by the same rule. An older version of the model document has the locks of its time and rebuilds with them, as it was, which Onshape gives as the reason for versions: "every change in the history of UsingDoc is also stable and recoverable" ([Linking documents](https://cad.onshape.com/help/Content/linked-documents.htm)). A lock is removed when its document is no longer imported, once the code parses and every imported document could be read. Pinning stays in the code, where the module says it itself; a lock is the tool's, and an [export](#export) writes the locked versions.
- **Lock writes are never undo steps:** `cad.locks`, and the `cad` field's creation alone, are among the undo manager's "Paths that are not undoable; changes only to them neither form steps nor end an undo run" ([`manager.ts`](../src/undo/src/manager.ts), `UNDO_IGNORE` in [`locks.ts`](../src/cad/src/model/locks.ts)).
- **Unavailable documents:** an import is the error on its line that it is today; a canvas or annotation is a marked row and pin. Neither is removed automatically. An annotation needs no lock: it is shown as its document is now, or at its pinned version.

### Security

- **An imported JS file runs** as model code, in the same sandbox once there is one ([05](05-sandboxing.md#approach)). Pinning it means a later change of that document can't change what runs without a visible edit of the model.
- **The tool reads every URL the code names, with the user's access.** [05](05-sandboxing.md#threat-model) forbids model code to "access documents the user did not hand to the model"; an import inserted by a drop is handed over, one that arrived with a collaborator's edit is not, which the sandbox's design has to settle.
- **An SVG is never put into the page as markup:** as a profile it is parsed to curves in the worker; as a decal or canvas it is drawn as an image, where "some browsers place restrictions": "JavaScript is disabled", "External resources (e.g., images, stylesheets) cannot be loaded" ([MDN](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image)).
- **An annotation runs the embedded document's tool,** as opening that document in Patchwork does.

### Export

A model with `automerge:` imports is "Portable only within the Automerge network" ([02](02-model-storage.md#imports-in-the-prototype)). The documents list is the manifest of an export: each imported document written next to the model as a file, and an import map from the URLs to the files. For runtimes without the attributes, it adds a loader: in Node 24.16.0, a `load` hook of `module.registerHooks` that returns `export default …` for `type: "text"` and `"bytes"` runs both imports unchanged (checked). Canvases and annotations are not exported; the module doesn't know them.

## Suggested order

1. **Text and bytes imports, the documents list and the document dialog** (As, Name, Version, preview) for imports, titles in the code pane. Done ([Implementation](#implementation)).
2. **Drop, paste and Insert,** with Import as the only role; picking a value for a field. Done ([Implementation](#implementation)).
3. **Annotations:** the cheapest of item 7's three, built from comment anchors, pins and the embed frame. Done ([Implementation](#implementation)).
4. **Canvases:** a textured plane, its dialog and Calibrate; no kernel work. Done ([Implementation](#implementation)).
5. **Sketch from SVG:** the richer `Profile` and picking among a sketch's profiles, as an item of its own before sketch constraints; then drops onto faces and planes.
6. **Decals:** appearance on bodies, the projector.
7. **Fonts and STEP/STL bodies,** with assemblies.

## Considered

- **Imports listed outside the code,** as openscad's `doc.imports`: rejected in [02](02-model-storage.md#verdict-imports-in-code); the list here is derived from the code.
- **The role from the drop target alone,** with a menu only where several fit: a drop into the view says little about what is meant, and a JS or data document could then only be imported through the code pane.
- **Copying on insert** (Fusion's SVG, OLE's embedding, Rhino's "Embedded"): loses the source's updates and the way back to it. Copying stays possible by duplicating the document in Patchwork and linking the copy.
- **Decals in the `cad` field:** simpler, but a decal that isn't in the code can't be placed by a parameter and is lost outside the tool.
- **Deriving the kind of module from the document's type** instead of an attribute, as JSON files are today: then the same file fails in a standard runtime after export.
- **PMI** (tolerances, surface finish on faces): a feature of its own, with drawings.
- **Canvases in the model's fit** (Home, the margins of a view, [20](20-view-framing.md)): each user shows or hides canvases for themselves, while views and Home belong to the model and frame the same for everyone.
- **Canvas preselected for an image dropped on a face:** a face suggests Decal for an image ([Dropping, pasting, inserting](#dropping-pasting-inserting)), so the image waits, and Canvas is one choice.

## Open

- SVG details: lengths without physical units, strokes versus fills, text (needs the font), `transform`s, self-intersecting paths as kernel failures ([04](04-kernel-robustness.md)); an XML parser for the worker, which has no DOM.
- Decals on curved faces, and which export formats can carry a decal.
- Whether a lock should hold back on every import error, failed feature and broken reference is for user testing.
- An editor that loaded the model before another's lock arrived writes the same lock again, which is harmless. A new model has its `cad` field ([`datatype.ts`](../src/cad/src/datatype.ts)); in a model without it, two editors that create the field at once keep only one's map, as for views and configurations, and a lost lock is written again with the next build.
- Whether a feature that uses a document shows that document's state icon on its timeline entry at all times, as the mark of what depends on something outside the model.
- Accessibility: without a drag, a document gets into the dialog only as a pasted URL, since Patchwork has no document picker a tool could open; once it has one, it belongs in the dialog's document field. Drags don't exist on touch ([11](11-adopting-shapes.md#touch)).
- A file dropped from the desktop onto the editor must become a file document first, as the sidebar makes one.
- Picks are of numbers for number fields and of any leaf without a field; picking a list or an object, and drops on fields that aren't numbers (text, vectors, a sketch's profile), are open.
- Annotations: pins on neighbouring faces may still overlap; changing a pending insert's role once chosen, and a document with several uses listing them in its dialog, are not built; whether `<patchwork-view>` shows a pinned annotation's version, rather than the latest, is untested; Patchwork's Comments panel doesn't list annotations, which aren't threads.
- Imported documents are prepared again in every build ([00](00-status.md#not-started)); bytes make that more expensive.
