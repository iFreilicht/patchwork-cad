# Parameters

How a model's parameters are managed in the editor, and how a parametrized model is used elsewhere in Patchwork: customized without editing it, kept as named sets of values, embedded, or driven by values from other documents. Implementation: [`model/params.ts`](../src/cad/src/model/params.ts), [`model/configurations.ts`](../src/cad/src/model/configurations.ts), [`configurations.ts`](../src/cad/src/components/configurations.ts), [`parameters.ts`](../src/cad/src/components/editor/parameters.ts), [`ParamsDialog.tsx`](../src/cad/src/components/editor/ParamsDialog.tsx), `paramSchema` in the feature library ([`params.ts`](../src/features/src/params.ts)); tests: [`params.test.ts`](../src/cad/test/params.test.ts), [`configurations.test.ts`](../src/cad/test/configurations.test.ts), [`sweep.test.ts`](../src/features/test/sweep.test.ts), [`cad-parameters.spec.ts`](../src/harness/e2e/tests/cad-parameters.spec.ts).

## Building with values

A model declares parameters as plain JS, as replicad does:

```js
export const defaultParams = { w: 60, d: 40, h: 8 };

export default function main({ w, d, h }) { … }
```

replicad-evaluator calls `main` with the module's own defaults when it gets no values (`module.default(params || module.defaultParams)`, `builder-DzkdSG9v.js`). A build request carries the values to show over them ([`protocol.ts`](../src/cad/src/kernel/protocol.ts)), and the worker's wrapper of `main`, which already records what it returns, merges them over the module's `defaultParams` (`withParams` in [`worker.ts`](../src/cad/src/kernel/worker.ts)), so replicad's call stays as it is. A trial build before moving a Custom Script uses the same values. Another model calls a model with its own values in plain JS: `body(() => m4.default({ ...m4.defaultParams, w: 80 }))` ([11](11-adopting-shapes.md#body)).

## Prior art

- **Fusion** has one dialog, Modify › Change Parameters, with "Favorites", "User Parameters" (set up manually) and "Model Parameters" (every dimension a feature has, generated by Fusion) ([GrabCAD tutorial](https://grabcad.com/tutorials/parametric-designing-in-fusion-360)). Naming a value in a feature's field creates a parameter, and user parameters "can reference one another" ([Product Design Online](https://productdesignonline.com/user-parameters-in-autodesk-fusion-360/)). Global parameters are "User parameters shared across multiple files" ([Fusion blog](https://www.autodesk.com/products/fusion-360/blog/mastering-fusion-parameters-a-guide-for-simplified-design-control/)).
- **Onshape configurations** "create variations of a part, Part Studio, assembly, or Variable Studio" from "independent inputs such as lists, checkboxes, and configuration variables"; "When inserting a configured part into an assembly, select the required configuration during insertion" ([Onshape help](https://cad.onshape.com/help/Content/configurations.htm)).
- **OpenSCAD's Customizer** reads metadata from comments: "Numbers=2; // [0, 1, 2, 3]" is a dropdown, "// [-10:0.1:10]" a slider, `/* [Tab Name] */` starts a tab, and the "Hidden" tab's parameters "are never displayed". Saved values go to a separate JSON file of named `parameterSets`, selected on the command line with `-p parameters.json -P model-2` ([OpenSCAD manual](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Customizer)).
- **replicad**'s share app shows `defaultParams` as a form: "a simple form will be offered to the user to change the parameters and customise the shape" ([Sharing models](https://replicad.xyz/docs/tutorial-overview/sharing-models/)). It has no ranges or units; its studio can draw dimension `labels` into the preview, because "Sometimes it is difficult to understand which dimension on a model a parameter can change" ([Studio features](https://replicad.xyz/docs/advanced-topics/studio-features/)).

## In the editor

### Where parameters are written

`defaultParams` stays the source of truth, for portability ([02](02-model-storage.md#design-goal-portable-models)) and because replicad's own tools read it. A parameter is two spans: a property of the `defaultParams` literal and a name in `main`'s destructuring. The editor edits both with minimal splices, as forms edit feature arguments:

- **Add:** append `k: v` to the literal and `k` to the pattern, on a line of its own if the literal has its properties on lines of their own; a model without them gets `export const defaultParams = { k: v };` before `main` and `main({ k })`.
- **Rename:** both spans, its key in [`paramConfig`](#kinds-units-ranges) and every use in `main` (a shorthand property that reads it keeps its key: `{ w }` becomes `{ w: width }`), and the parameter's values in every [configuration](#configurations-and-named-views-in-the-model-document) in the same change. A parameter `main` reads under another name, `{ w: wide }`, changes only its key.
- **Remove:** only when `main` doesn't use it; the dialog disables the button and says why.
- **Promote a value:** "ƒ" next to a feature's number field turns `radius: 1.5` into `radius: radius` and adds `radius: 1.5` to the parameters, under the argument's name or a numbered one if it is taken.

New names must be valid and unused in the model ([`clashes`](../src/cad/src/model/refactor.ts)). Models that deviate (`main(params)` with `params.w`, a computed `defaultParams`, defaults in the pattern) still build; the dialog then shows the parameters and says why it can't edit them.

### Derived parameters

Fusion's parameters reference each other. An object literal can't (`{ w: 60, d: w * 2 }` is a `ReferenceError`). Derived parameters are constants at the start of `main`:

```js
export default function main({ w, d, h }) {
  const r = w / 4;
  const t = Math.min(h, 3);
  …
}
```

The editor reads the leading run of `const x = <expression>` statements as the derived parameters, instead of a Custom Script entry ([`derivedStatements`](../src/cad/src/model/analyze.ts)): expressions that call nothing but `Math.…`, define no function, assign nothing and make no object or array, which later code could change (a Custom Script that sets `hole.r` stays one). They show in the parameters entry below the independent ones, where they are added (after the others), renamed with their uses, removed when unused, and their expressions edited. They are not overridable: a configuration sets independent parameters only, and derived ones follow. Each derived value is one statement with one expression span, so a future expression language replaces only the expression.

- **A `derive` function** (`export const derive = ({ w, h }) => ({ r: w / 4 })`, called by `main` itself because callers pass only `defaultParams`) encapsulates them, but makes the code harder to read and needs machinery to keep `main`'s call to it working.
- **Destructuring defaults** (`main({ w = 60, d = w * 2 } = {})`) make derived values overridable and tie them to JS's default-value semantics.

### Kinds, units, ranges

A form needs a field kind, and a customizer wants ranges, steps, units, descriptions and groups. They describe which inputs the model accepts, like a function's signature, so they live in the code, where other callers can read them at runtime, e.g. to check values they pass through `body()`. The model exports them as plain data, sparsely, and the editor infers whatever is missing:

```js
export const defaultParams = { w: 60, d: 40, h: 8 };
export const paramConfig = { w: { title: "Width", minimum: 10, maximum: 200, multipleOf: 5 }, r: { title: "Corner radius" } };
```

- **Field names are JSON Schema's** (`title`, `description`, `minimum`, `maximum`, `multipleOf`, `enum`), plus `unit`, so form generators, validators and LLM tooling understand them without our tool.
- **Absent fields mean no constraint,** as in JSON Schema, so callers read `paramConfig` as it is. Default values stay in `defaultParams` only, not in a `default` field. A kernel-free library function `paramSchema(model)` merges the portable parts into a complete JSON Schema for callers that want one: `type` from each default value, `default` from `defaultParams`, the rest from `paramConfig`.
- **Inference fills the rest in the editor only** ([`quantities`](../src/cad/src/model/params.ts)): a name used in a feature argument of kind `length`, `profile` or `plane` ([`ParamSpec`](../src/features/src/schema.ts)) is a length, in one of kind `number` a number, and a derived parameter passes its quantity on to the names its expression uses. A parameter used as both stays a plain number. Inferred values are never written back into the code, where they would go stale when usage changes. A model without `paramConfig` still gets a useful panel.
- **Units follow from the quantity.** Values are bare numbers: OCCT, replicad and the feature schemas (`kind: "length"`) have no units. The library fixes them, as Fusion's per-design default units do, but for every model: lengths are millimetres and, once features take angles, angles are degrees, which exporters rely on. Values in `defaultParams` and configurations are always in these units. The editor infers a parameter's quantity (length, angle, count) from its use and shows its unit, so `unit` is needed only where that can't work: as a label for quantities that aren't geometry (`"teeth"`, `"%"`), and later for showing a length in another unit (`"in"`), which the panel converts on input and display while the code keeps millimetres. JSON Schema has no unit keyword, and validators ignore unknown keywords, so `unit` costs nothing there.
- **Derived constants** are described by name, too, for their title and unit; they get no ranges, as they aren't set.
- **The dialog uses** `title` next to the name, `description` as its tooltip, `unit` over the inferred one, and `minimum`, `maximum` and `multipleOf` to mark a shown value outside them.
- **Drift:** a parameter's name is in `defaultParams`, `main`'s pattern and `paramConfig`. The editor's rename changes all three; a rename typed in the code pane leaves a stale key. A rename in the code editor itself (F2, as in other editors), which the code pane wants anyway, would cover that case.

Rejected:

- **Comments**, OpenSCAD-style (`w: 60, // [10:200:5] Width`) or as JSDoc tags on `main`: a grammar inside comments is a DSL ([02](02-model-storage.md#design-goal-portable-models)); JSDoc has no tags for ranges or units, and nothing reads either at runtime.
- **Library helpers** (`w: length(60, { min: 10 })`, `defaultParams = defaultsOf(params)`): one place per parameter, but every value is wrapped in a call, a replicad-only model needs our library for its parameters, and derived constants would need wrapping too.
- **A document field** (`cad.params`): lost on export and invisible to other callers, though it describes the model; drifts from the code as `paramConfig` does.
- **Objects in `defaultParams`** (`w: { value: 60, minimum: 10 }`): breaks every caller and `main`'s arithmetic.

### The parameters entry

`main`'s signature is the model's input as `return` is its output ([15](15-bodies.md#output)), so the timeline has a first entry, "params", mirroring the return entry at its end; neither is one of the code's entries, and neither can be dragged. Its dialog takes the place of a feature's and the return's, with two tables. **Parameters:** a row per parameter with its name, its default, its override in the shown configuration, its final value and its unit. **Derived values:** a row per derived parameter with its expression, final value and unit. Final values are what the last build computed: the worker records the argument `main` got, and [`prepare.ts`](../src/cad/src/kernel/prepare.ts) makes each derived constant report its value on its own line. With the defaults shown, the dialog edits the code: defaults and expressions are fields, names are renamed with F2 or a double click, and parameters and derived values are added and removed; there is no override column. With a configuration shown, it edits only that configuration's overrides: the default and the expression are text, an override is a field that is empty when the configuration sets nothing, and each table has "Switch back to Defaults to edit". Under each table, "Edit code" opens the code pane at its part of the code: `defaultParams`, or the derived values at the start of `main`, which are in different places; code between the derived values and the features, also a `const` after it, is a Custom Script entry in the timeline after the parameters entry ([`params.test.ts`](../src/cad/test/params.test.ts), [`cad-parameters.spec.ts`](../src/harness/e2e/tests/cad-parameters.spec.ts)). A Fusion-style modal is the alternative; a dialog in the view keeps the view free while values change.

### Configurations in the dialog

A value written to `defaultParams` changes the model for every collaborator; a configuration overrides some of them. Which configuration a user shows the model with is theirs alone, kept in tool storage like the marker (`params` in [`DocUiState`](../src/cad/src/types.ts), [10](10-view-state.md#storage)): one user shows "Wide" while another shows the defaults. The dialog's "Configuration" picker and the browser's Configurations section choose it, and the status bar says `Shown with configuration "Wide"`. An override takes JSON, or an automerge URL for a [linked value](#values-from-other-documents); an empty field takes the default. "Save as new configuration" adds a configuration with the shown one's overrides, or none from the defaults, and shows it. The viewer tool, which embeds a model, shows its defaults; an embed shows its own configuration.

Two other designs were confusing in use. A layer of values each user tries over a configuration, to apply to the defaults or a configuration later: a configuration then kept only the values tried before it was saved, and the dialog's most visible column edited the defaults, which every configuration followed, so editing one configuration seemed to edit them all. And one column of values per configuration next to editable defaults: it left unclear which field edits what, and derived values, which no configuration sets, looked like parameters.

### Parameters stress references

Changing a parameter is a fuzzer for topological naming ([03](03-topological-naming.md#recommendation)). Some references carry absolute coordinates, which a changed dimension moves away from: `piece(notch, 1, { near: [49.75, 0, 20] })` in M1, and `faceAt(near)` for adopted bodies, which picks the face "whose centroid was nearest to `near`" ([`refs.ts`](../src/features/src/refs.ts)). A loop parameter (M3's `ribs`) changes which features exist. Lenient builds pass a failed feature's input through ([07](07-poc-modelling-ui.md#the-feature-library)), so a configuration can look plausible and be wrong; the editor, the viewer and embeds therefore show the build's problems in the status bar.

The sweep ([`sweep.test.ts`](../src/features/test/sweep.test.ts)) builds M1, M3 and M4 with each numeric parameter scaled by 0.25, 0.5, 0.75, 0.9, 1.1, 1.25, 1.5, 2 and 3, and M3 with five other rib lists: 125 builds, 11 of which break, each for one of three reasons:

| Reason | Builds | What happens |
|---|---|---|
| The geometry the reference names is gone | 8 | M1's notch leaves the plate or sits on its edge (`w` × 0.25 and × 0.5, `a` × 0.25, × 2 and × 3), so the edge or the face pieces it splits don't exist; M3's rib leaves the bracket (`w` × 0.25 and × 0.5); `ribs = []` makes no `rib0`. The reference reports "nothing matches", correctly: the design changed. |
| A `near` hint vetoes the right piece | 2 | `w` × 3 in M1 and M3: the piece index still names the right piece, but the hint's absolute point is now nearer another piece's centroid. Without the hints, M1 with `w` = 180 resolves the chamfer's edge to the same entity as with 60 (index 15); with them, it is "ambiguous". |
| OCCT fails | 1 | M3's fillet with `d` × 0.25: the rib reaches past the base ([04](04-kernel-robustness.md)). |

No reference resolved to a visibly wrong entity, but the sweep can't tell a wrong entity from a right one; the hints are what would. They fail safe, and too early: hints relative to the part's size, or ones that only decide between candidates instead of vetoing, would survive scaling.

## In Patchwork

### Use cases

1. **Customize:** share a model so others pick values (a box for their drawer) but can't change the geometry.
2. **Named sets:** keep sets of values, e.g. M3×10 and M4×20 of one bolt, as Onshape configurations do; and named views, as Fusion keeps them in the design.
3. **Embed:** show a model with a particular set of values, seen from a particular view, in a note, a canvas or a slide.
4. **Drive:** take values from other documents: a spreadsheet cell, a number in a note, a shared dimension that several models use (Fusion's global parameters).
5. **Compare:** see configurations side by side.

Using a configured model inside another model is the step towards assemblies and is out of scope here ([below](#considered)).

### Building blocks

- **Automerge URLs address parts of a document.** A URL carries a path and heads, `automerge:<docId>/<path>#<heads>` ([`AutomergeUrl.ts`](../node_modules/.pnpm/@automerge+automerge-repo@2.6.0-subduction.48/node_modules/@automerge/automerge-repo/src/AutomergeUrl.ts)). Path segments are keys, indices (`@0`), matches (`{"id":"alice"}`) and, last, cursor ranges (`[2@abc-5@def]`) into text ([`parser.ts`](../node_modules/.pnpm/@automerge+automerge-repo@2.6.0-subduction.48/node_modules/@automerge/automerge-repo/src/subdoc-handles/parser.ts)). `repo.find` resolves all of them: "A URL can carry both fixed heads (`#h1|h2`) and a path suffix (`/a/@0/b`). Layer the heads projection first … then scope to the path" ([`Repo.ts`](../node_modules/.pnpm/@automerge+automerge-repo@2.6.0-subduction.48/node_modules/@automerge/automerge-repo/src/Repo.ts)).
- **Cursors are robust with a fallback.** A cursor range survives edits inside and around it, collapses to `""` when its text is deleted, even if an undo inserts it again, and throws when the whole string is reassigned ([13](13-collaboration.md#anchors-under-edits)). Our own reordering deletes and re-inserts a statement ([`moveEntry`](../src/cad/src/model/splice.ts)), which collapses cursors inside it. A cursor never resolves to the wrong text, though; it resolves or visibly collapses.
- **Sub-documents have a precedent.** A comment thread lives in the commented document's `@comments`, carries `"@patchwork"?: { type: "comment-thread" }`, and is rendered by its own tool from its sub-document URL: `<patchwork-view doc-url={threadUrl} tool-id="comment-thread">` ([CommentsView.tsx](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/comments-view/src/CommentsView.tsx)). Its datatype exists so that "a thread opened on its own (its `@patchwork.type` is `comment-thread`)" resolves a title and a tool ([index.ts](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/comments-view/src/index.ts)). `<patchwork-view>` passes its `doc-url` to `repo.find` unchanged ([`legacy-impl.ts`](../node_modules/.pnpm/@inkandswitch+patchwork-elements@6.0.3_@automerge+automerge-repo@2.6.0-subduction.48_@i_26a2e581e79e92a2830f32430f224fad/node_modules/@inkandswitch/patchwork-elements/src/legacy-impl.ts)).
- **No excerpt embedding exists.** Patchwork's `embed` package embeds whole documents with a tool; patchwork-base and patchwork-experiments have no transclusion of a part of a document.
- **Models import data and JS documents** through our loader ([02](02-model-storage.md#imports-in-the-prototype)), not through the service worker, because the model runs from a blob URL. Patchwork's service worker serves any document at `/<encoded automerge URL>/<path>`: a document with `content` as that content with its `mimeType`, e.g. a JS file of Patchwork's `file` datatype, and any other document as JSON ("anything else gets JSON.stringify'd", [`resolve.js`](../node_modules/.pnpm/@inkandswitch+patchwork-filesystem@0.2.13_@automerge+automerge-repo@2.6.0-subduction.48_@automerge+automerge@3.4.1/node_modules/@inkandswitch/patchwork-filesystem/dist/resolve.js)). Paths only walk folder and directory documents, not keys of a document. A model document therefore keeps its code in `content` with the `mimeType` `application/javascript`, which Patchwork's `file` datatype gives a `.js` file, and is served as its module; its `@patchwork.type` stays `cad-model`, which alone picks the default tool: `getFallbackTool` sorts the tools whose `supportedDatatypes` include `getType(doc)`, which is `doc["@patchwork"]?.type` ([`tools.js`](../node_modules/.pnpm/@inkandswitch+patchwork-plugins@1.2.6_@automerge+automerge-repo@2.6.0-subduction.48_@au_824dc6e957b16f34fe03caae82a99381/node_modules/@inkandswitch/patchwork-plugins/dist/tools.js)). `cad-tools` checks that the CAD Editor opens a new model, that the service worker serves it as `application/javascript`, and that `import()` of that URL runs it. Whether model code reaches the service worker by a dynamic `import()` or `fetch()` is a question for the sandbox ([05](05-sandboxing.md)).

### Document fields and portability

A model document is a map, and the code is its `content` field ([`CadModelDoc`](../src/cad/src/types.ts)). Data the tool owns can sit next to it in a plain field. Keys starting with `@` are left to metadata that any document can carry, whatever its type: Patchwork's code uses only `@patchwork` (type, title, drafts) and `@comments`, which the comments provider reads on every mounted document. Fields merge per key, while code merges per character: two users changing `w: 60` to 70 and to 80 at once can merge to `7080` in the text, while a field keeps one of the two values.

The cost is portability: the model run elsewhere sees only `content`. That is accepted for named sets of values and named views, which serve the tool, as OpenSCAD keeps its `parameterSets` in a JSON file next to the `.scad`. Exporting a model can write them out as such a sidecar file or as `export const configurations = {…}`.

### Configurations and named views in the model document

The model document holds both lists, under one field:

```ts
cad: {
  configurations: { id: string; name: string; params: { [name: string]: ParamValue | { link: AutomergeUrl } } }[];
  views: { id: string; name: string; camera: CameraState }[];
}
```

- **One mechanism for both.** Configurations and named views are stored, listed in the browser, picked per user and embedded the same way ([18](18-named-views.md)). The browser's Configurations section lists "Defaults" first and then the configurations, with "+" (a new configuration from the shown one), a click to show the model with one, only for this user, a context menu that renames and deletes a configuration, and a grip that drags one out as an embed, "Defaults" too.
- **Kept in sync.** A rename in the editor renames the parameter in every configuration in the same change. A rename typed in the code pane leaves values under the old name, which then have no effect.
- **Configurations override independent parameters only;** a parameter one doesn't override, also one added later, takes the default, so a changed default changes it in every configuration that doesn't override it. Hovering a configuration in the browser hovers the parameters entry.
- **Values, not expressions.** A configuration is data in the `cad` field, not code, so each of its values is a literal or a [link](#values-from-other-documents) to a number in a data document. Unlike a default in `defaultParams`, it can't be an expression, refer to another parameter, or read an import, e.g. a JS file's export (`import { hole_diameter } from "automerge:…"`); a JS file dropped on a configuration's value is a problem line ([21](21-embedding.md#dropping-pasting-inserting)).
- **Drafts** fork the document copy-on-write (`CloneEntry`: "One COW relationship between an original doc and the per-draft clone", [`draft-types.ts`](../.claude/skills/writing-patchwork-tools/reference/patchwork-base/drafts/src/draft-types.ts)), so a draft carries its configurations with its geometry.
- **Saving changes the model document,** so a configuration or view is shared with everyone who can open the model. Patchwork has no permissions yet, so read-only access is not considered.

### Embedding: proxy documents

An embedding document refers to a configuration and a view through a small proxy document, the embed document of [18](18-named-views.md#embeds) (`cad-model-embed`), which gets a `configuration`:

```ts
{ title: string; model: AutomergeUrl; configuration?: string; view?: string }
```

Both are ids into the model's lists, and each is optional: no configuration means `defaultParams`, no view means the viewer's framing. Dragged out of the Views section, an embed has a view; out of the Configurations section, a configuration. The viewer shows it with a picker for each, which changes the embed, and builds with the configuration's values.

- **For:** works wherever Patchwork takes a document (sidebar, drag and drop, the default tool by datatype); has its own title; carries its choice separately from the model, so several embeds of one model differ.
- **Live by default:** the proxy follows the model's latest version, as Patchwork's embeds do. Pinning is the user's choice: a model URL with `#heads`.
- **A deleted target:** when the configuration or view is gone, the proxy keeps no copy of its values; its picker says "Deleted configuration" or "Deleted view" and offers the model's others, and the model shows with its defaults meanwhile.
- **"Can't edit anything else"** is a UI restriction: the proxy holds the model's URL, which opens in the editor, too.
- **Orphans:** creating a proxy on a drag that is then cancelled leaves an orphan document ([18](18-named-views.md#embeds)).

The alternative, an embed that stores a sub-document URL such as `automerge:<model>/cad/configurations/{"id":"k3"}` and no proxy, would follow the comment threads' pattern and leave no orphans. It needs a `@patchwork.type` on each entry and a tool that loads the model from the sub-handle's `documentId`, and it is unverified whether the sidebar, drag and drop and the default tool lookup accept such URLs. It can't combine a configuration with a view, which a proxy can. An experiment worth running, not the plan.

### Values from other documents

A configuration's value can be a link instead of a literal: `{ link: AutomergeUrl }`, any URL that resolves to a number, pasted into its field. That covers a field in a structured document (`automerge:<sheet>/rows/@3/width`) and a number in text (`automerge:<note>/content/[2@abc-4@abc]`), whose range must parse as a number. Fusion's global parameters are then just a document of numbers that several models' configurations link to; no special datatype is needed.

- **Resolving:** the tool finds each linked URL with `repo.find`, which resolves the path to the value, and rebuilds when the sub-handle reports a change ([`configurations.ts`](../src/cad/src/components/configurations.ts)). A link that doesn't resolve, a collapsed range, or text that isn't a number is a broken value: the status bar says why, the field is marked, and the build uses the default.
- **A link into text breaks when its number is typed anew.** Replacing "42" by "45" deletes the range's characters, so its cursors collapse ([13](13-collaboration.md#anchors-under-edits)) and the link reads `""`, while a link into a field follows every change ([`configurations.test.ts`](../src/cad/test/configurations.test.ts)). Links into text suit numbers that are edited in place, not retyped.
- **Only in configurations.** `defaultParams` has no links, so the model stays portable; a model that needs the value everywhere imports the document as data instead ([02](02-model-storage.md#imports-in-the-prototype)), which a document dropped on a parameter's default does ([21](21-embedding.md#dropping-pasting-inserting)).
- **Picking a link:** a document dropped on a configuration's value opens the document dialog, whose data tree picks one of its numbers; the link is that value's URL, `automerge:<id>/rows/@1/width` ([21](21-embedding.md#dropping-pasting-inserting)). A drag whose URL names a number already is linked at once; dragging a value out of another tool needs that tool to offer such a URL, e.g. a text selection as a cursor range, which Patchwork's text editor already makes for comments (`handle.sub("content", cursor(from, to)).url`, [13](13-collaboration.md#data-model)). Pasting a URL works everywhere.
- **Units and typing** are the linked document's business: `"12 mm"` is not a number, and the link breaks.
- **Ephemeral values:** the cards' shared context ([spec](../.claude/skills/writing-patchwork-tools/reference/patchwork-experiments/cards/spec.md), [09](09-patchwork-26-features.md#where-the-features-live)), "named channels of pure JSON state that any component can read (aggregated) or write (scoped)", would let a slider card on a canvas drive an embedded viewer without saving anything. A playground, not storage.

### Considered

- **Separate variant documents** (`{ model, params }`, one per set of values): the model can't see them, so a parameter renamed in the model orphans their values with no way to find and map them; and views and configurations would be spread over many documents.
- **Drafts as variants:** drafts are meant to be merged back; a never-merged draft drifts from main, I found no operation that brings the original's later changes into a clone, and nothing keeps a draft to parameter changes. A good tool for "try a redesign", not for configurations.
- **Variants as code** (a variant that imports the model and calls it): outputs and further features would come for free, but the variant then is an assembly of one part, which blurs the line between configurations and assemblies; and several code texts in one document that import each other need module resolution inside a document, which [02](02-model-storage.md#verdict-imports-in-code)'s imports don't solve.
- **Configurations as code** (`export const configurations` next to `defaultParams`), so that their values can be expressions and read imports ([Values, not expressions](#configurations-and-named-views-in-the-model-document)), with each configuration's resolved values cached in the document for tools that don't run the model. Kept as data until users need it, for what it costs:
  - **A stale cache:** values that read a followed document change without an edit of the code, and only an open editor recomputes them, so the cache would need the bookkeeping of locks ([21](21-embedding.md#following-and-pinning)). Derived parameters, which are computed in `main`, would need a build to cache.
  - **Ids:** embeds name a configuration by its id; a configuration keyed by name in code breaks them when it is renamed in the code pane.
  - **Merging:** concurrent edits of a value merge as text ([Document fields and portability](#document-fields-and-portability)).
  - **Code the editor can't read,** e.g. `{ ...base, w: 80 }`, would need a fallback such as the Custom Script entry.
  - **Named views** would stay data, splitting the one mechanism both share.
- **Values in the embed itself** (`<patchwork-view params="…">`): `<patchwork-view>` passes only a document and a tool id ([10](10-view-state.md#instance-identity)), so values must live in a document.
- **Configured models inside models** (dropping a configuration into the editor inserts an import and `body(() => m.default({ ...m.defaultParams, ...values }))`, as Onshape picks a configuration on insertion): belongs to assemblies.

### Costs

Every open proxy builds the model in its own kernel worker, and each worker holds an OCCT instance (warm load 100–200 ms, 0.9 s in Firefox, [08](08-module-evaluation.md#conclusions)). A canvas of ten configurations is ten workers. Sharing one worker between views of the same page, or caching meshes per model heads and parameter values, would bound it. Opening a proxy runs the model's code, as opening the model does ([05](05-sandboxing.md)).
